# Hike Planner 3D: working notes

A hiking planner PWA in plain JavaScript: no build step, no framework, no backend. It is published by GitHub Pages from `main` (root) at https://stefanblaj54-crypto.github.io/hike-planner-3d/ and installed on the owner's phone from that address. The owner is not a developer: he asks for changes in plain language, and pushing to `main` is how a change goes live.

## How a change goes live

- Push to `main`. GitHub Pages republishes in about a minute. `.nojekyll` skips Jekyll, so files are served as they are.
- The installed app checks for changes each time it opens or comes back to the screen (`checkUpdate` in js/app.js asks `check()` in sw.js). The service worker downloads the app's own files again, which is everything it keeps except `lib/`, `fonts/` and `icons/`. If any file changed, it swaps them all in at once and tells the page. The page reloads straight away on the hikes list or About; anywhere else it shows a toast and reloads when the person goes back to the list.
- An ordinary change needs no version bump in sw.js. Do bump `VERSION` in js/app.js for each release: it shows in About and in the menu.
- Bump `VERSION` in sw.js only when a file is added, removed or renamed, or when anything in `lib/`, `fonts/` or `icons/` changes, because those are kept as fixed and only a new service worker refreshes them. Regenerate the offline file list at the same time, from the repository root:

```sh
python3 - <<'EOF'
import os, re, json
fs = ['./', 'index.html', 'app.css'] + sorted(os.path.join(r, f) for d in ['fonts', 'icons', 'img', 'js', 'lib'] for r, _, n in os.walk(d) for f in n if not f.endswith('.txt')) + ['manifest.webmanifest']
s = open('sw.js').read()
s = re.sub(r'const SHELL=\[.*?\];', lambda m: 'const SHELL=' + json.dumps(fs, indent=2) + ';', s, flags=re.S)
open('sw.js', 'w').write(s)
EOF
```

- Keep every path relative (`./`). The site lives under `/hike-planner-3d/`, not at the root of the domain.
- The page only reloads by itself on the hikes list or About, and never twice within 30 seconds, so a host that changes files on every request cannot cause a reload loop.

## Files

- `index.html`: every screen (`home`, `new`, `build`, `view`, `custom`, `about`, `inv`, `detail`), the live guide layer (`#guide`), the header, menu drawer, sheet, dialog, the resume bar (`#resume`) and toast. Scripts are classic scripts loaded in order: theme.js in `<head>`, then core, build, trail, viewer, guide, motion, app.
- `app.css`: all styles. Colours, radii and text size come from CSS variables that js/theme.js sets, so themes and the Customize screen work everywhere. Don't hard-code colours in components. The look (since 1.6) is a dark sports-watch dashboard in the manner of the WHOOP app: black, graphite cards, figures big and labels in small capitals (`.micro`), dials (`.ring`), strips of figures (`.kpis`), and one signal scale: `--good`, `--fair`, `--bad` for how good something is, `--eff` for effort, `--sun` for daylight. Keep text short: a figure or a chart first, words only for labels and alerts.
- `js/theme.js`: themes, accent colours, route palettes, the sky by time of day, and the home-screen skyline drawn from the next hike's real elevation profile. Settings live in localStorage `hp-look`; `lv` marks the settings version: a look saved before 1.5 (no `lv`) moves once from the skyline and rows to the 3D picture and cards, and one before 1.6 (`lv` < 3) to the Carbon theme. Carbon (the default) is always dark: pure black, graphite cards, white main buttons, the red trail mark (`--mark`). Exposes `HP.look`.
- `js/core.js`: the `HP` namespace, IndexedDB `hike-planner-3d` (stores `hikes`, `plans`, `blobs`), reading GPX/KML/GeoJSON, GPX export and helpers in `HP.u`, `HP.sunTimes` (sunrise and sunset in local clock hours, the 3D view's sun model), `HP.effort` (km-effort: km plus 100 m of climbing per point; under 15 easy, 15–25 moderate, 25–35 hard, over 35 very hard) and `HP.compass` (a bearing as N, NNE, …). The inventory (since 1.8): `HP.INVCAT` lists the kinds of kit in groups (clothing, footwear, gear, for the nights, always with me), `HP.INVK` by key, and `HP.inv` keeps the person's items in localStorage `hp-inv` as `{v:1,items:{<kind>:[{name,g}]}}`. The first item of a kind is the one the advice names: `HP.inv.word(kind,fallback)` gives it as `<span class="own">`, or the general word when there is none. `HP.maps` (since 2.2) holds the topographic maps shared by the 3D view, the planning map and the live guide: `inCH` and `boxCH` (Switzerland's border, simplified; a box is Swiss when its corners, side middles and centre are), the tile addresses `swiss` (`ch.swisstopo.pixelkarte-farbe`), `outdoor` (Esri's Outdoor map: 512-pixel tiles, level z with the detail of z+1) and `otm`, their credits (`CREDIT`), Esri's shared failure count (`esriFail`, `esriOk`, `esriOff`) and `leaflet(map)`, which puts them on a Leaflet map: from zoom 11 the Swiss map inside Switzerland (128-pixel tiles one zoom closer, so twice the detail, as on its own site), Esri's Outdoor map around it, each tile from the one source that has it, OpenTopoMap when Esri is off, and the credits of the maps in view. A failed Esri tile is fetched once more to see why, so only Esri's own refusals count, not a lost connection. `HP.ESRI_KEY` is the owner's ArcGIS key (see ArcGIS below). `HP.maps.stripLayer(map,id,pane)` draws a hike's saved Swiss map from the phone only (never the network), and `HP.maps.routes(map)` the marked hiking routes of Waymarked Trails (since 2.3). Since 2.3 also: `HP.log`, a short record of what went wrong (window errors, unhandled rejections, the app's own `console.warn` with an error, failed network calls by host, failed builds, storage and backup problems; the last 40, in localStorage `hp-log`, with keys cut out and positions rounded to about 1 km), shown by "Copy problem details" in About (`problemText` in app.js); `HP.fetchT(url,opt,ms,as)`, one network helper with a time limit for every request (tiles 15 s, JSON 30–90 s, the router 90 s) that the caller's own signal (Cancel) also stops, which `HP.fetchJSON` is built on (localStorage `hp-tmul` scales every limit, for tests); `HP.backup` (`make`, `restore`): every hike's list entry and plan, the inventory and the look in one JSON file, typed arrays as base64 (`enc`/`dec`), pictures and saved maps left out; restore adds hikes this phone lacks and replaces those the file has a newer copy of, merges the inventory and keeps this phone's look. A full phone is said plainly (`why` in `HP.db`). `HP.db` gained `putMany`, `keys(prefix)` and `delPrefix(prefix)`, and `remove` deletes a hike's saved map too. Each hike keeps the blobs `<id>:sat` (satellite JPEG), `<id>:topo` (the map picture: the Swiss national map when the whole model lies in Switzerland, else OpenTopoMap; `D.topoSrc` says which), `<id>:relief` (used for the list picture when there is no satellite picture), `<id>:dem` (the heights at the elevation tiles' full detail: Uint16 in 0.2 m steps above `D.dem.min`, `D.dem.w` × `D.dem.h`, rows from north to south) the home-screen pictures `<id>:cover` (900 × 1125) and `<id>:coverw` (1600 × 900), and since 2.3 the map for no signal: `<id>:m:<z>/<x>/<y>` (Swiss map tiles) or `<id>:vec` (OpenStreetMap lines and places), described by `D.strip` (`kind`, `n`, `bytes`, `at`).
- `js/build.js`: building a plan. `HP.fetchExtras` gives hikes saved before 1.4 their satellite picture and detailed heights the first time they open with a connection, and hikes in Switzerland saved before 2.2 the Swiss national map as their map picture (`D.topoTry` counts failed tries, three at most). `loadMapPic` makes the map picture: the Swiss map at up to zoom 16 when the whole model lies in Switzerland, else (or when swisstopo can't answer) OpenTopoMap. Tile downloads (`loadTiles`) give up on a server after 8 failures in a row with nothing loaded (16 later on), and don't retry a tile that timed out before anything loaded, so a server that is down or hangs costs seconds, not minutes; the terrain step then fails with a plain message and Try again, the pictures are simply left out. The records, the forecast and the forecast runs are asked for together. `HP.route` says when the router is busy, down or too slow (with Try again on the planning map), and `HP.easier` throws rather than claiming "no easier way" when the router didn't answer at all. `HP.strip` (since 2.3, `plan`, `save`, `remove`, `tiles`, `kindOf`): the map for no signal. When the whole model lies in Switzerland it saves the Swiss national map's tiles along the route (zoom 15 ±1.5 km, 16 ±600 m, 17 ±250 m; about 1,100 tiles and 30 MB for the Bärentrek), six at a time, skipping those already saved; elsewhere it saves the paths, roads, streams, lakes, glaciers, cliffs, huts, shelters, water, peaks, passes and signposts within 600 m of the route from Overpass (`HP.overpass`, from trail.js) for the guide to draw (OpenTopoMap and the OSM tile servers don't allow saving tiles for offline use). `hutOf` keeps each hut's, refuge's or campsite's phone, website, opening_hours, beds, reservation and operator in `D.huts` (by name; `D.hutsAt`), and `HP.hutInfo` fetches them for hikes saved before 2.3. `HP.backTrip(D,q,signal)` (since 2.4) finds the way back from the end of the route to its start: when both ends lie in Switzerland, the stops nearest them and the connections from an hour before you can be at the stop (arrival on the last day plus the walk to it) and the last one of the day, from transport.opendata.ch (`odch`, `nearStop`, `conn`; the `fields[]` filter keeps answers small). That timetable announces a window a few months ahead but often has nothing near its end, so a date more than 60 days ahead isn't asked for, and one outside the window after all (a 400 naming it) or one that comes back empty uses a stand-in too: the same weekday one or two weeks from today (`standIn`, kept as `pt.typ`). Elsewhere the nearest train station (5 km) and bus stop (2.5 km) at each end from Overpass (`osmStops`); everywhere the drive back with BRouter's `car-fast` profile (`carBack`; a car-free end such as Wengen answers "target island", kept as `car.none`). The result is `D.back` (`key`, `ends`, `kind` 'ch' or 'osm', `pt`, `car`); the stops and the road are reused while the ends stay put. `HP.backPick(B,arr)` gives the first connection you can still catch after arriving at `arr` (clock hours), the last one of the day, whether it is missed and the margin. Covers BRouter routing, terrain heights, the topo texture, places on the way (Overpass), and the day split (dynamic programming that prefers huts and villages for nights). It also holds the weather: forecast, ECMWF ensemble, ERA5 climate records, weather types (`HP.WXT`, `HP.wxClass`) and their percentages. Since 1.8 the forecast also brings the wind at 850 and 700 hPa (about 1,500 and 3,000 m: `w8s`, `w8d`, `w7s`, `w7d`, with heights `z8`, `z7`), and the records each day's dominant wind direction and strongest wind (`wd`, `ws`). `HP.climWind(clim,date,type)` gives a weather type's usual wind direction from the days of that type within 30 days of the date, and how steady it is; `HP.fetchClimWind` adds the record winds to hikes saved before 1.8.
- `js/motion.js` (since 2.1): how the app moves. `HP.motion.vt(update,{type,from,to,name})` wraps a DOM change in a view transition (`document.startViewTransition`; Chrome 111+, Safari 18+) and sets `html[data-vt]` so app.css picks the animation: `push` (the new screen slides over from the right, the old one moves a little left and dims, as on iOS), `pop` (the reverse), `expand` (a card grows into its page: the card gets the name `surface`, the page's `.detsurf` and `#detail` get `surface` and `detc`; the shape is the image pair's own background, graphite deepening to black), `collapse` (back into the card), `hero` (a hike's picture grows into the 3D view, both named `pic`) and `fade`. The header is named `top` in every transition, so it stays in place and its title crossfades. Without the API the new screen slides or fades in with the Web Animations API. Presses: a pointerdown on anything pressable shrinks it at once (`scale`, by its size: small buttons 0.95, cards about 0.98) and it springs back on release (a `linear()` spring, damping 0.68); a scroll that starts on it cancels the press. Overlays come in with CSS keyframes on `:not([hidden])` and leave through `HP.motion.close(el,done)`, which plays `.out` and then hides; `HP.motion.open(el)` cancels a close in progress, so use these two instead of setting `hidden` on the drawer, sheet, dialogs, toast, guide and its SOS box. `slider(box)` gives segmented controls and chip rows one indicator (`.segi`) that slides to the chosen option, even across redraws (positions kept by the control's id or first `data-k`). `dragDismiss(box,onClose)`: the hike's menu follows a finger down and closes past a quarter of its height or on a flick. `edgeBack(getPage,goBack)`: a touch from the left edge of a detail page, About, Customize or Inventory drags the page right and goes back past a third of the screen (touch listeners are added only for such a touch). Everything honours `prefers-reduced-motion`, and only transform, opacity and colours animate. The home dials fill once per visit (`drawRings` in app.js); the 3D view shows the hike's own picture until its first frame (`stagePicture`, `.stage.ph`, `.live`), so the picture that grew from the list comes alive; the safety card shimmers while the trail is checked.
- `js/trail.js` (since 2.0): the trail check. `HP.trailCheck(D)` asks Overpass for the OpenStreetMap ways along the route (a union of small boxes, 0.6 km pieces with 60 m around them), the hiking routes they belong to, and the features beside them (cliffs, glaciers, `hazard`, fords, guideposts, rescue points); in Switzerland also the closures and diversions of the Swiss hiking trails (geo.admin.ch identify on `ch.astra.wanderland-sperrungen_umleitungen`), and the countries of the start and end (Nominatim, one request at a time). `analyse` matches each route point to the nearest way within 32 m that runs the same way (a 40 m grid of segments, with a penalty for switching ways and for unmarked roads; gaps of up to 3 points filled, one-point flickers removed), then keeps per point the way's character (`pw` into `paths`: highway, SAC grade, visibility, the waymark `sym` from `osmc:symbol`, marked, informal, access), the waymark runs (`marks`), the hazards (`hz`: `vf`, `aid`, `glacier`, `hazard`, `acc`, `ford`, `inf`, `off` for stretches with no mapped path, `vis`, `closed`, and `cliff` with `top` when the route runs along the edge rather than the foot; a cliff is drawn with its top on the left), the junctions (`junc`: nodes shared by two or more ways, with the turn as S, SL, SR, L, R, HL, HR, KL or KR, `key` when a wrong turn is easy, `town` in villages, and the nearest signpost's name and height) and the stretches on roads. `HP.osmcWords` and `HP.osmcSVG` put a waymark into words (in Switzerland: yellow signs, white-red-white marks, white-blue-white marks) and draw it. In Switzerland it also asks for the official hiking trails (swisstopo's swissTLM3D, `ch.swisstopo.swisstlm3d-wanderwege`, geo.admin.ch identify with the route as a line, in 2 km pieces, three at a time; since 2.3) and keeps per point `ofc`: 2 on an official alpine trail when that is clearly the nearest, 1 on an official trail, 0 not (the layer only names alpine trails; ordinary and mountain trails both come as plain trails). The result (`HP.TRAIL_V`, 2 since 2.3) is kept in `D.trail`, so it works offline; an older version still serves (`trailOK`) and is checked again with a connection.
- `js/viewer.js`: the 3D view (three.js r147), walking times, weather simulations, the readout, the day table and the line colours. How the ground is drawn:
  - The ground is a quadtree of Web Mercator tiles (`TILES`), like a web map: tiles split where the camera is close and merge where it is far, with separate tests for the mesh (vertex spacing on screen) and the picture (tile size on screen), some hysteresis, and only for tiles in view. Each tile's heights come from `<id>:dem` (the plan's coarse grid until that is read), with skirts so cracks between levels don't show. Far away every tile shows the picture saved with the hike; close up a tile loads its own picture: for Satellite, SWISSIMAGE aerial pictures from swisstopo up to zoom 18 in and around Switzerland, and ArcGIS World Imagery up to zoom 18 elsewhere and wherever a Swiss picture fails (since 1.9). For Topo (since 2.2) tiles load their own picture at every distance while there is a connection, so near and far look the same: the Swiss national map where the drawn part of the tile lies wholly in Switzerland (`t.ch`; each picture from the four tiles one zoom closer, drawn into 512 pixels), else Esri's Outdoor map (512 pixels), and OpenTopoMap when Esri fails; without a connection the saved picture shows. 512-pixel pictures count twice towards the number kept. `prov(t)` gives the pictures to try for a tile, best first, and `t.pf` counts each one's failures for that tile (a 404 just means no picture at that zoom, so the larger tile's shows). The Swiss map and Esri's Outdoor map get a second try after 2.5 s; a Swiss tile that still fails shows its larger tile's Swiss picture, never another map's style. Tiles that gave up for want of a connection try again 30 s later, or as soon as the phone is back online (a 404 is final), and a new saved picture is swapped in under the live tiles without reloading them (`TILES.refresh`). Tile pictures are fetched six at a time and the least recently used are dropped. `follow()` keeps the orbit point on the ground and the camera above it when close.
  - Moving around: OrbitControls handles only the mouse (drag turns, right-drag moves, wheel zooms); its `touches` are switched off and touch has its own handling. One finger moves the map so the ground under the finger stays under it, and a flick glides on (its speed comes from the finger's own events, not the frame rate). Two fingers moving together turn the view (sideways) and tilt it (up and down), a twist turns it, and a pinch zooms about the ground between the fingers; each of these starts only past a small threshold, and the fingers are applied once per frame (`touchStep`), both together.
  - The shading detail comes from a texture baked once on the GPU from `<id>:dem` (or from the grid until that is read): red and green hold the slopes for per-pixel light, blue holds how much open sky each point sees (ambient occlusion). It is baked again when the height exaggeration changes. All tiles share one material set up by `WXV.prep`; `uMapRect` says which part of a tile's (or an ancestor's) picture to use.
  - Map styles: `uStyle` 0 = satellite (lightly graded), 1 = topo, 2 = relief, which the shader draws itself from height and slope (treeline and lasting snow from the latitude, contour lines on WebGL 2).
  - One sky colour function (`SKYF`) draws the sky, the haze over distant ground and the soft edges where the model fades into the sky, so they always match. Lambert materials don't get three's `cameraPosition`, hence `uCamP`.
  - The shadow map is fitted to the terrain as the sun sees it, and is redrawn only when the sun moves. The plain map lights the scene from the front left of the first view.
  - Fog sheets, rain and snow fade at the model's edges too. Clouds fade as the camera comes close, turning to light mist rather than a dark smear.
  - Weather (since 1.7, `initWX3D`): two pictures are drawn once on the GPU when the view opens (`bakeTex`). One is the cloud sprites: three cauliflower clusters and a fibrous sheet, holding the surface normal (red, green), how open the surface is (blue, crevices dark) and density. The other is a tileable noise for the cloud and fog layers.
    - Cumulus and storm towers are camera-facing sprites lit per pixel: sun on the side that faces it, blue-grey sky light in the shade, ground light from below, a silver edge against the sun. Each puff carries how much sun reaches it (lower and far-side puffs less), its cloud's flat base (cut in world height, so it stays level from any angle) and how thick its cloud is (storm clouds get dark bases). Anvils are flat sheets in the world, stretched downwind. A cumulus is built from a few large sprites, so it keeps one clear sunlit side.
    - Cloud and fog layers are a lit sea of billows from the noise; peaks rise through with soft, ragged shores (from the height texture `hmT`). Cloud on the slopes (decks, fronts) tints the ground with wisps and a ragged base.
    - Lightning: a jagged channel with forks (`LineSegments2`, additive) and a soft glow of points, in one to four return strokes, only the first lighting the forks; flashes inside the cloud light it from within. Its light on the cloud (`uBolt`) and the ground (`uBoltG`) is stronger in the dark (`flashK`). `V3.strike(true)` makes a strike and holds it, for screenshots.
    - Rain: thin streaks, brightest at the falling end; shafts under storm cells blow downwind at the bottom. Snow: flakes of many sizes that flutter. Below the cloud, falling rain or snow veils the ground with the distance the view travels through it (`uPrK`). Snow on the ground thins on steep slopes and in forest, with rock outcrops and the ground's own light and dark showing through.
  - Wind (since 1.8, `windSetup`, `windBase`, `windAt`): a mass-consistent model in the manner of WindNinja on the plan's coarse grid. The wind above the hills (`windBase`: the forecast's 850/700 hPa winds at ridge height, or for a weather type the direction its days had in the ERA5 records) is made to flow over the terrain by solving ∇·(h∇λ) = −∇·(h v0) with SOR, once each for an east and a north wind and for a stable and a neutral lid, blended by stability. On top: windward speed-up and lee shelter in the manner of MicroMet (exposure from a terrain-position index), channelling along valleys (their axis from the smoothed terrain's curvature), and slope breezes when the wind is light (up by day, down at night). In forecast mode the field is matched to the forecast's 10 m wind at its points (inverse-distance weights on the speed ratio and the turning). Gusts are the forecast's gust margin on top of the local wind. `cond()` uses `windAt` for the readout (its arrow `.warr` turns with the view), the walking times and the wind trails; `WFC` caches it by weather, month, day, hour and forecast issue. `V3.wind(i)` and `V3.windGrid(nx,day,t)` are for tests.
  - Best views (`bestViews`, kept in `D.views` with its version `VIEWS_V`, the route's length and the number of known summits): from points every 200 m, rays over the heights in 48 directions score how far you can see, how high the mountains stand around, how deep the ground drops, whether you stand on a crest, and which named summits are in clear sight. Each day gets its best view if it is a good one, then the best of the rest, at least 2.5 km apart (2 to 6 in all). Each keeps the way with the most to see (`az`) and the skyline's height there (`el`); `viewName` names it after the place it is at or the nearest named place along the trail. The card `#viewscard` and the page `views` list them with buttons to look from there.
  - First person (since 1.8, `fpEnter`, `fpStep`, `fpExit`): the camera walks the route 12 m above the ground at true height (1×, the height setting comes back afterwards), looking 160 m ahead and a little down or up with the slope, at 30 m/s (120 at 4×), with the light and weather of the hour you are there. It stops 5 s at each best view, turned towards it and looking up at the skyline, and 3 s at the end of each day (`fpStops`, which follow changes to the plan). Drag to look around (it eases back while walking), pinch or scroll to zoom; Escape leaves and space pauses. While it runs the canvas's pointer events are taken for looking around (capture listeners), OrbitControls is off, the route lines move down to the ground (`position.y = −13`), the near plane goes to 4 m, and the weather's haze and cloud fog act as for a close view from above (`fogD`). Picking a point on the profile or a day moves the walker; the flyover (`▶ Walk`) and first person don't run together. `V3.look(k)` stops at view k, `V3.firstPerson(km)` walks from km, `V3.fp()` reports the state for tests.
  - Safety (since 2.0, `safety()`, cached by `SAFEK`): runs the trail check when a hike opens with a connection and the check is missing or over 60 days old (`runTrail`; a route from a file gets its grades from it when 60% of it is matched). The grade at each point is the mapped SAC grade, and in Switzerland at least what the waymarks mean (yellow T1, white-red-white T2, white-blue-white T4); tracks and roads count as T1. Findings: T4 and up (bad), T3 (warn), via ferrata, glacier, closure (bad), ladders and chains, hazards, private paths, stretches with no mapped path (bad over 500 m), poor visibility, cliff edges (warn, a note on T1), rock faces above the path, stream crossings (one note), unofficial paths, long unmarked stretches, very steep path (`SLOPE` 22° and up), and the most remote point (half the walking time between huts, villages, lifts, roads and the ends). Steep drops come from the terrain (`exposure()`, needs the detailed heights `HGT`): the gentlest of three 15 m steps from 10 to 55 m out on the lower side, 42° and up where the path is not T1; the terrain alone never makes a route "not for beginners". Edges, drops and steep path inside a T3 or alpine stretch become part of it. Since 2.3: an official Swiss alpine trail followed for 150 m or more is white-blue-white (T4) whatever the tags say; stretches in Switzerland off its signed network over 400 m (roads aside) are a note, and the share on official trails counts the Swiss part only; and old snow from the winter (`snowAt`): typical for the date and height (`SNOWD`, `oldSnowLine`: in the Alps most passes clear between mid-June and early July; 60 m lower per degree north of 46.5°), 200 m lower on slopes facing north and 150 m higher facing south (`facing`, from the detailed heights), "likely" above that line and "possible" up to 300 m below it; near the date the forecast models' snow on the ground (`fcSnowLine`) takes over, and where it shows none the typical snow counts one step less. Old snow is one finding a day, a warning (with the date and height in words; from late November to February it speaks of the season's snow instead), and not for beginners only where the forecast shows snow lying on steep or demanding ground; it adds gaiters, poles and (steep) microspikes to the packing list. The verdict: Suits a beginner, Take care in places, Not for beginners. The card `#safecard` (a strip along the route, the hardest grade, how much is marked, the junctions, the three worst findings, the waymarks to follow, the emergency numbers by country, `SOS`), the page `safety` (the profile coloured by difficulty, the findings day by day with Show on the map, the waymarks in order, the junctions as a turn sheet for each day, help, Open the live guide, Check the trail again), the day's alerts (the two worst findings of the day, made red when the weather there is wet, snowy or stormy) and the line colours `safe`. `V3.exposure()` and `V3.heightAt(x,y)` are for tests; `HP.viewer.safety()` reports the findings, `HP.viewer.show(i)` goes to a point, `HP.viewer.state()` hands the live guide what it needs.
  - Huts (since 2.3): `seasonOf` reads the month ranges of an opening_hours tag (open and off), `openOn` says whether a date falls in them, `hutLine` shows phone, website, beds, season and booking on the days page; the day's alerts say when tonight's hut is usually closed on that date (with its phone) or invite to book it. `fetchHuts` gets the details once for older hikes. The alerts card opens with a reminder to save the map for no signal from three weeks before the hike (`stripNudge`; saving it is `stripAsk`/`saveStrip` in app.js, with its progress in `#xpill`).
  - Getting back (since 2.4): the card `#backcard` (`renderBackCard`: next departure, travel time, changes, the last one, the walk back; hidden for a loop, where the ends lie within 400 m) and the page `back` (`backDetail`: the first connection you can catch leg by leg with platforms and walks, two later ones, the last of the day, the stand-in note, Check again, Google Maps and SBB links; the road; on foot, the same way back). `fetchBack` runs when a hike opens, when the phone comes online and 1.5 s after the cards are drawn, and asks again when `backKey` changes (the dates, the ends, the arrival in 2-hour steps), after 7 days, or 10 minutes after a failure; a hike that is over isn't looked up. The walk back (`backWalk`, `revSeg`, `revT`): the route reversed and timed with the same DIN model at your pace (climbs and descents swap), sleeping at the same places in reverse from the day after the last day, with each day's typical weather (`HP.wxDay` past the hike's days), sunset, the huts' seasons on those dates, the biggest climb going back (`backClimbs`) and the safety findings placed on the way back (`backWhere`). ## Data sources

All are free. All but one need no key: BRouter (`hiking-mountain` profile), Overpass and Nominatim (also for the trail check), the Swiss hiking trail closures (geo.admin.ch, open government data), the Swiss national map for the maps in Switzerland (swisstopo, `ch.swisstopo.pixelkarte-farbe`, free with the credit), OpenTopoMap tiles, AWS Terrain Tiles (terrarium), Sentinel-2 cloudless 2025 by EOX (`tiles.maps.eox.at`, zoom ≤ 13, free for personal use with the credit shown), SWISSIMAGE by swisstopo (`wmts.geo.admin.ch`, open government data, free with the source credited; it covers Switzerland and some of the land around it), Open-Meteo for the forecast, the ensemble (`ecmwf_ifs025`) and the archive (ERA5), Waymarked Trails (`tile.waymarkedtrails.org/hiking`, the marked routes on the planning map, CC-BY-SA), the Swiss public transport timetable (`transport.opendata.ch`, from search.ch, CORS, no key; for getting back), swisstopo's official hiking trails (geo.admin.ch, open government data), and from Esri, with the owner's free-tier key (see above), ArcGIS World Imagery (`ibasemaps-api.arcgis.com`, close-ups outside Switzerland) and the Outdoor map (`static-map-tiles-api.arcgis.com`, `arcgis/outdoor`, the topographic map outside Switzerland while there is a connection).

## Testing

The tests are Playwright scripts in `tests/`, run in headless Chrome. They use `/usr/bin/google-chrome` if it exists; otherwise set `CHROME` or let Playwright use its own Chromium. Weather and Overpass calls are mocked in `tests/mocks.py`, because the archive API rate-limits and Overpass times out from sandboxes. ArcGIS pictures are made-up pictures (`tests/esri_mock.jpg` for World Imagery, `tests/esri_outdoor_mock.png` for the Outdoor map) so tests don't use the key's allowance; `ESRI=live` lets them through. `V3.orbitAt(i,dist,az,pol)` points the view at route point i, for screenshots. Run them from the repository root:

```sh
pip install playwright --break-system-packages   # if missing
python3 -m http.server 8777 &                    # serves the repository
python3 tests/redirect_server.py &               # port 8778, a host that redirects index.html
BASE=http://localhost:8777/ python3 tests/test_app.py desktop    # also: mobile, offline
BASE=http://localhost:8778/ python3 tests/test_app.py offline
python3 tests/test_misc.py
python3 tests/test_home.py full                  # also: empty
python3 tests/test_home2.py
python3 tests/test_wx_prob.py
python3 tests/test_update.py                     # serves its own copy on 8791; OLD=<folder or zip> also tests a switch from an older version
BASE=http://localhost:8777/ python3 tests/test_extras.py   # a hike from before 1.4 gets its satellite picture and heights
python3 tests/test_touch.py                      # one finger moves the map, two fingers turn, tilt, twist and pinch
BASE=http://localhost:8777/ python3 tests/test_v18.py   # inventory, the pages behind the cards, the wind, best views and first person
BASE=http://localhost:8777/ python3 tests/test_guide.py  # the trail check, safety and the live guide with a simulated GPS
BASE=http://localhost:8777/ python3 tests/test_v21.py    # the easier way, page transitions, presses, sliding indicators, overlays, reduced motion
BASE=http://localhost:8777/ python3 tests/test_maps.py   # the Swiss map, Esri's Outdoor map and OpenTopoMap on the planning map, in 3D and in the guide
BASE=http://localhost:8777/ python3 tests/test_resilience.py   # each online service down, refusing or hanging; Cancel; tiles coming back; memory
```

BRouter is mocked with a path that bows out to one side (`mocks.brouter`); `BROUTER=live` lets the real router answer. In the test browser the 3D view draws slowly (software WebGL), so check motion on screens without it, or pause the transition's animations (`document.getAnimations()`) and draw chosen moments, as the motion checks did. The trail check's Overpass query is answered from real OpenStreetMap data around the Bärentrek (`tests/osm_baerentrek.json.gz`, ODbL); geo.admin.ch and Nominatim's country lookup are mocked too; the official Swiss hiking trails are answered from real swisstopo data along the Bärentrek (`tests/swiss_trails_baerentrek.json.gz`, collected in November 2026), and the stand-in huts carry phones, websites and seasons. The Swiss timetable is a stand-in too (`mocks.transport`: connections every hour at :14 until 21:14; more than 100 days ahead a 400 with the window, 40 to 100 days ahead empty), as are the stations and bus stops abroad (`mocks.stops`) and the road (`mocks.brouter` with `car-fast`; Wengen answers "target island"). `tests/test_guide.py` feeds positions with `HP.guide.fix` and once through the browser's own geolocation.

Screenshots go to `tests/shots/`, which git ignores. Look at them after any visual change: the 3D view and the home screen break easily in ways the scripts don't catch.

## Conventions

- Interface text is plain and in sentence case, with no jargon. The person using it is a beginner hiker.
- Units are metric, the minus sign is `−`, and steepness is shown in degrees.
- The 3D view should look premium: real light and shade, haze with distance, no hard edges. Check changes there on phone-sized and desktop screenshots.
- Keep the app working offline for saved hikes, and keep it fast on a phone.
- Commit messages say what changed for the person using the app.
